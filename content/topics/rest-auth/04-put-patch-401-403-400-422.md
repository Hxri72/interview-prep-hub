## 💡 What is it?

These are three pairs that interviewers love, because they sound alike.

- **PUT vs PATCH:** both update. PUT **replaces the whole thing**. PATCH **changes some fields**.
- **401 vs 403:** both say "no". 401 means **"log in first"**. 403 means **"you're logged in, but not allowed"**.
- **400 vs 422:** both mean "bad input". 400 means **"I can't read this"**. 422 means **"I can read it, but it breaks a rule"**.

## 🏠 Real-life example

**PUT vs PATCH — your school ID card.**
- **PUT** = the office prints a **brand-new card** from the form you filled. If you left "blood group" empty, the new card has no blood group.
- **PATCH** = the office sticks a **small correction label** on the address only. Everything else stays.

**401 vs 403 — the school staff room.**
- **401** = the guard says, "Who are you? Show your ID card."
- **403** = the guard reads your card: "You're a student. Students can't enter the staff room."

**400 vs 422 — handing in an exam form.**
- **400** = the form is torn and smudged. The teacher **can't read it**.
- **422** = the form is neat, but you wrote your age as **-5**. It's readable, but it **breaks a rule**.

## 🧑‍💻 Code example

All three pairs in one small Express 5 app. Run `npm init -y` and `npm install express`. Save as `compare.js` and run `node compare.js`. (CommonJS.)

```js
const express = require('express');                                  // load Express
const app = express();                                               // create the app
app.use(express.json());                                             // parse JSON; broken JSON → error with status 400

const users = { 'token-asha': { name: 'Asha', role: 'recruiter' } }; // fake logins: token → user
let job = { id: 1, title: 'Node Dev', city: 'Kochi', open: true };   // one job in our "database"

function auth(req, res, next) {                                      // checks WHO is calling
  const token = (req.headers.authorization || '').replace('Bearer ', ''); // read "Bearer <token>"
  req.user = users[token];                                           // find the user for this token
  if (!req.user) return res.status(401).json({ error: 'Please log in' }); // 401 = we don't know you
  next();                                                            // known user → continue
}                                                                    // end of auth

function onlyAdmin(req, res, next) {                                 // checks WHAT they may do
  if (req.user.role !== 'admin') return res.status(403).json({ error: 'Admins only' }); // 403 = known, not allowed
  next();                                                            // admin → continue
}                                                                    // end of onlyAdmin

app.patch('/jobs/1', auth, (req, res) => {                           // PATCH = change some fields
  if ('open' in req.body && typeof req.body.open !== 'boolean') {    // a rule: open must be true/false
    return res.status(422).json({ error: 'open must be true or false' }); // 422 = readable JSON, breaks a rule
  }                                                                  // end of rule check
  job = { ...job, ...req.body };                                     // keep old fields, overwrite sent ones
  res.json(job);                                                     // send the updated job
});                                                                  // end of PATCH

app.put('/jobs/1', auth, (req, res) => {                             // PUT = replace the whole job
  job = { id: 1, ...req.body };                                      // only what was sent survives
  res.json(job);                                                     // send the new job
});                                                                  // end of PUT

app.delete('/jobs/1', auth, onlyAdmin, (req, res) => res.status(204).end()); // only admins may delete

app.use((err, req, res, next) => res.status(err.status || 500).json({ error: err.message })); // errors → their code

app.listen(3000, () => console.log('listening on 3000'));            // start on port 3000
```

Testing it with `curl` (Asha's token is `token-asha`, and she is a recruiter, not an admin):

```text
PATCH {"city":"Pune"}         → {"id":1,"title":"Node Dev","city":"Pune","open":true}
PUT   {"title":"Node Dev"}    → {"id":1,"title":"Node Dev"}
DELETE, no token              → {"error":"Please log in"} 401
DELETE, Asha's token          → {"error":"Admins only"} 403
PATCH  '{"open": tru'         → {"error":"Unexpected end of JSON input"} 400
PATCH  {"open":"yes"}         → {"error":"open must be true or false"} 422
```

**What to notice:** after PUT, `city` and `open` are **gone**, because PUT replaces everything. PATCH kept them.

## 🔍 Deeper version

**PUT vs PATCH in detail**

| | PUT | PATCH |
|---|---|---|
| Body | The **full** new resource | Only the changes |
| Missing fields | Removed or reset to defaults | Left as they were |
| Idempotent? | ✅ Always | ❌ Not guaranteed |
| Can it create? | Yes, if the client chooses the id/URL | Normally no |
| Typical use | "Save the whole settings form" | "Change job status to closed" |

With Mongoose, PATCH is usually `findByIdAndUpdate(id, { $set: changes })`. PUT is `findOneAndReplace` (or `replaceOne`). Always **whitelist** the fields a client may change. Otherwise someone can PATCH `{ "role": "admin" }`. This is called **mass assignment**.

**401 vs 403 in detail**

- **401 Unauthorized** really means **unauthenticated**: no token, a bad signature, or an expired token. The standard says a 401 response should include a `WWW-Authenticate` header that tells the client how to log in (e.g. `Bearer`). Cookie-based APIs often skip it.
- **403 Forbidden** = authentication worked, but **authorization** failed: the role, plan or ownership rules say no.
- The order in middleware is: **authenticate first** (401), **then authorize** (403). See [Authentication vs authorisation](topic:rest-auth/authn-vs-authz) and [RBAC](topic:rest-auth/rbac).

In a multi-tenant product, the token often includes the **tenant**. If a token from Company A is used on Company B's subdomain, the server must reject it. SkillKeepr locks the tenant inside the JWT and checks it on every request.

**400 vs 422 in detail**

| | 400 Bad Request | 422 Unprocessable Content |
|---|---|---|
| Problem | Syntax: broken JSON, wrong content type, can't parse | Meaning: parsed fine, but breaks business or validation rules |
| Examples | `{"open": tru`, a string where the schema needs an object | `experience: -5`, invalid email, end date before start date |

Many APIs (and many Joi/Zod setups) send **400 for all validation errors**. That's acceptable. What matters is being **consistent and documented**, with a clear error body like `{ code, message, details }`. See [one consistent response format](topic:express/response-format).

## 🎯 Why do we use it?

- **The frontend reacts correctly.** 401 → go to login or refresh the token. 403 → show "You don't have access". 422 → highlight the wrong form field.
- **No accidental data loss.** Using PATCH for partial updates means a half-filled form can't wipe out other fields.
- **Clear contracts.** API users know exactly what each response means.

## ⚠️ Common mistakes

- **Using PUT with a partial body** and wiping fields by accident.
- **Sending 401 for "no permission".** Users get logged out when they're only missing a role.
- **Sending 403 for "not logged in".** The frontend never sends the user to the login page.
- **Not whitelisting PATCH fields**, so clients can change `role`, `tenantId` or `price`.

## 🗣️ How to answer in an interview

> "PUT replaces the whole resource, so any field you don't send is gone. It's idempotent. PATCH only changes the fields you send, so I use it for partial updates like changing a job's status. With PATCH I always whitelist which fields can change, to avoid mass assignment.
>
> 401 means not authenticated: no token, or it's invalid or expired. 403 means the user is authenticated but not allowed, like a recruiter trying an admin-only action. My middleware authenticates first and returns 401, then checks permissions and returns 403. The difference matters, because the frontend logs out on 401 but just shows 'no access' on 403.
>
> 400 is for requests the server can't parse, like broken JSON. 422 is for valid JSON that breaks validation rules. Some teams use 400 for both. I just keep it consistent and return a clear error message."

## 🔁 Follow-up questions

### Is PATCH idempotent?

Not by definition. "Set city to Pune" can be repeated safely. "Add 1 to the view count" cannot. PUT is always idempotent.

### Should you return 403 or 404 for another user's private record?

Often **404**, so you don't reveal that the record exists. Use 403 when it's fine for the user to know it exists, like "you can see this job, but you can't edit it".

### What happens when a token expires — 401 or 403?

**401.** The user's identity can't be proven any more. The frontend should refresh the token or send the user to log in.

### How do you stop a client from PATCHing fields they shouldn't?

Validate the body with a schema (Joi or Zod) that lists only the allowed fields. Strip or reject everything else. Never pass `req.body` straight into the database update.

## ✅ Quick check

### 1. A candidate's record is `{ name, email, city }`. The client sends `PUT` with `{ name, email }`. What happens to `city`?

:::answer
It is **removed** (or reset). PUT means "this is the whole new version". Use PATCH to keep `city`.
:::

### 2. The JWT's signature is valid, but the user's role is `candidate` and the route needs `recruiter`. Which code?

- A) 400
- B) 401
- C) 403

:::answer
**C) 403.** The user is authenticated (the token is valid), but not authorized for this route.
:::

### 3. The body is `{"email": "not-an-email"}`. 400 or 422?

:::answer
**422** if you separate them: the JSON is valid, but the value fails a rule. **400** is also acceptable if your API uses 400 for all validation errors. Stay consistent.
:::
