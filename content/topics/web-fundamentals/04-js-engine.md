## 💡 What is it?

A **JavaScript engine** is the program that runs your code. Chrome and Node.js both use [V8](glossary:v8).

V8 doesn't run your text directly. It first turns it into **bytecode** and runs that. Then it watches which functions run a lot, and **compiles them into fast machine code**. This page opens the engine so you can see each step.

## 🏠 Real-life example

Think of a **new delivery boy in your area**.

- On day one he **reads the address list** word by word = parsing the source code.
- He draws a **simple map** of the streets = the AST (a tree of your code).
- He writes **step-by-step directions** and follows them = bytecode run by the interpreter (Ignition).
- After a week, some routes are **daily routes**. He learns **shortcuts** for them = hot functions compiled to machine code (Maglev, TurboFan).
- His shortcuts assume "**house 12 is always the blue one**" = the guess that objects keep the same shape.
- One day the house is **painted red**, and he gets confused. He goes back to the slow directions = deoptimisation.

## 🧑‍💻 Code example

**Part 1 — see the bytecode.** Save as `bytecode.js`:

```js
function addTax(price) {          // a tiny function we want to inspect
  return price * 1.18;            // add 18% tax
}                                 // end of addTax
console.log(addTax(100));         // call it once so V8 compiles it to bytecode
```

Run it with V8's debug flags. Node passes them straight to V8:

```bash
node --print-bytecode --print-bytecode-filter=addTax bytecode.js   # show the bytecode of addTax only
```

Real output on Node 24 (V8 internals; addresses shortened):

```text
[generated bytecode for function: addTax (0x… <SharedFunctionInfo addTax>)]
Bytecode length: 6
Parameter count 2
   74 S> @    0 : 13 00             LdaConstant [0]
   87 E> @    2 : 41 03 00          Mul a0, [0]
   94 S> @    5 : b3                Return
Constant pool (size = 1)
           0: <HeapNumber 1.18>
118
```

Your one line became **3 bytecode instructions**: load the constant `1.18`, multiply it by the first argument `a0` (`price`), and return. ("Parameter count 2" includes the hidden `this`.)

**Part 2 — watch V8 optimise, then deoptimise.** Save as `jit.js`:

```js
function area(shape) {                       // reads w and h from an object
  return shape.w * shape.h;                  // multiply width by height
}                                            // end of area
let total = 0;                               // running sum
for (let i = 0; i < 200000; i++) {           // call it many times so it becomes "hot"
  total += area({ w: i, h: 2 });             // same object shape every time: { w, h }
}                                            // end of loop
total += area({ h: 2, w: 3, extra: true });  // a different shape: keys in another order, plus one more
console.log('total', total);                 // print the result
```

```bash
node --trace-opt --trace-deopt jit.js   # print when V8 optimises or throws away fast code
```

Real output, filtered to `area`:

```text
[marking <JSFunction area> for optimization to MAGLEV, reason: hot and stable]
[completed compiling <JSFunction area> (target MAGLEV)]
[marking <JSFunction area> for optimization to TURBOFAN_JS, reason: hot and stable]
[completed optimizing <JSFunction area> (target TURBOFAN_JS)]
[bailout (kind: deopt-eager, reason: wrong map): begin. deoptimizing <JSFunction area>]
total 39999800006
```

The story in the output:
1. `area` ran many times with the **same shape**, so it became "**hot and stable**".
2. V8 compiled it with **Maglev** (a quick optimiser), then with **TurboFan** (the strongest one).
3. The last call used a **different shape** (`{ h, w, extra }`). The fast code's guess failed. "**wrong map**" means "wrong hidden class". V8 **deoptimised** it.

## 🔍 Deeper version

**The pipeline inside V8:**

```text
source text
   │  scanner → tokens   (function, addTax, (, price, ), {, return, …)
   ▼
parser → AST             (a tree: FunctionDeclaration → ReturnStatement → BinaryExpression *)
   ▼
Ignition → bytecode      (runs right away; collects "feedback": which types and shapes it saw)
   │   hot code + stable feedback
   ▼
Sparkplug → Maglev → TurboFan   (faster and faster machine code, built in the background)
   │   a guess breaks (new shape, new type)
   ▼
deoptimise → back to bytecode → may optimise again later
```

| Tier | What it is | Trade-off |
|---|---|---|
| **Ignition** | Interpreter that runs bytecode | Starts instantly, runs slower |
| **Sparkplug** | Very fast, simple compiler from bytecode to machine code | Quick to build, modest speed-up |
| **Maglev** | Mid-level optimising compiler | Good speed, builds fast |
| **TurboFan** | Top optimising compiler | Fastest code, slowest to build |

The trace above shows two of these tiers working for real: Maglev, then TurboFan.

**Lazy parsing.** V8 doesn't fully parse every function at start. It quickly "pre-parses" inner functions and fully parses them only when they're first called. That's one reason big bundles still start reasonably fast, and one reason [smaller bundles](topic:web-fundamentals/what-is-bundler) start faster.

**Hidden classes (V8 calls them "maps") and inline caches.**
- `{ w: 1, h: 2 }` and `{ w: 5, h: 9 }` share one hidden class: "w at slot 0, h at slot 1".
- When `shape.w` runs, V8 remembers "for this hidden class, `w` is at slot 0". That memory is an **inline cache**.
- If the same line only ever sees **one** shape (monomorphic), it's fastest. A few shapes (polymorphic) is a bit slower. Many shapes (megamorphic) is slow.
- `{ h: 2, w: 3 }` is a **different** shape from `{ w, h }` because the **order** differs.

**Garbage collection** runs alongside: short-lived objects are cleaned quickly in the "young generation". See [where variables live](topic:web-fundamentals/memory-stack-heap).

**Where the engine ends and the runtime begins.** V8 knows only the language: objects, functions, promises. `setTimeout`, `fetch`, `document` and `fs` come from the **host** — the browser or Node.js. See [JS in the browser](topic:web-fundamentals/browser-runtime), [JS in Node.js](topic:web-fundamentals/node-runtime) and the shorter intro [how JavaScript runs](topic:javascript/how-js-runs).

## 🎯 Why do we use it?

You don't control the engine, but knowing it helps you:
- explain **"is JS interpreted or compiled?"** correctly in interviews
- write **hot code** (loops over thousands of items, data mapping) that stays fast
- understand why **startup time** depends on bundle size (parsing and compiling cost time)
- read performance profiles in DevTools, where "Compile" and "Parse" show up as real costs

## ⚠️ Common mistakes

- **Saying "JavaScript is just interpreted."** Modern engines compile hot code to machine code at run time (JIT).
- **Building objects with keys in random orders,** or adding keys later in a hot loop. This creates many shapes and slows reads.
- **Using `delete obj.key` in hot code.** It can change the object to a slow "dictionary" mode. Set the value to `undefined` instead, if you only need it empty.
- **Micro-optimising everything.** Most code isn't hot. Measure with a profiler first; only tune the parts that really run a lot.

## 🗣️ How to answer in an interview

> "V8 is a JIT engine. It scans the source into tokens, parses it into an AST, and generates bytecode that the Ignition interpreter runs immediately. While running, it collects type feedback. When a function becomes hot and its feedback is stable, V8 compiles it to optimised machine code — Maglev first, then TurboFan for the hottest code.
>
> That optimised code relies on assumptions, like objects always having the same hidden class. If an object with a different shape shows up, V8 deoptimises and falls back to bytecode. So in performance-critical code I keep object shapes consistent — same keys, same order — and keep types stable.
>
> And the engine only runs the language; things like setTimeout, fetch or fs come from the host — the browser or Node.js."

## 🔁 Follow-up questions

### What's the difference between an engine and a runtime?

The **engine** (V8) runs the JavaScript language. The **runtime** wraps the engine and adds APIs and an event loop: the browser adds the DOM, `fetch` and timers; Node.js adds `fs`, `http`, `process` and libuv. See [browser vs Node runtimes](topic:web-fundamentals/browser-vs-node-runtime).

### Why can a function get slower after it has already been fast?

It was optimised for certain shapes or types. When different ones arrive, V8 deoptimises it. If the input keeps changing, it may stay in slower code.

### Do other browsers use V8?

Chrome, Edge, Opera and Node.js use V8. Firefox uses **SpiderMonkey**. Safari uses **JavaScriptCore**. Bun also uses JavaScriptCore. They all follow the same JavaScript standard (ECMAScript), but have different internals.

### Why does a large bundle slow down page start even after download?

The engine must **parse and compile** the code before running it. More code means more parsing work on the main thread, which delays the first interaction. That's why code splitting helps.

## ✅ Quick check

### 1. Do these two objects share a hidden class: `{ id: 1, name: 'A' }` and `{ name: 'B', id: 2 }`?

:::answer
**No.** The keys are the same, but the **order** is different, so V8 gives them different hidden classes.
:::

### 2. What does "reason: wrong map" mean in a `--trace-deopt` line?

:::answer
The optimised code expected objects with a certain hidden class ("map"), but got an object with a **different shape**, so V8 threw the optimised code away.
:::

### 3. True or false: V8 compiles every function to machine code before running your program.

:::answer
**False.** V8 starts by running bytecode in the Ignition interpreter. Only **hot** functions are compiled to machine code later, while the program runs.
:::
